# 编辑边界

这里处理保真润色和指定范围编辑中容易误改的情况。用户要求纠正或评议内容时，按本轮问题重新判断，已确认内容和指定编辑范围仍保留。通用要求和输出方式以 [SKILL.md](../SKILL.md) 为准；没有这些疑问时不必读取。

## 通用编辑方法

按本轮委托区分保真润色、纠正内容、评议和重写。保真润色沿用作者的实质意思和语气，默认作最小必要修改。用户要求按当前问题改好一份答复时，重新判断原有内容怎样回答这个问题。助手自行添加的判断、自评、提醒和安排不因写进旧答就成为用户已确认的立场；用户已确认的内容、明确要求保留的表达及指定的编辑范围仍然有效。

润色时保住以下内容：

- 事实与判断、谁对什么做了什么、数字对应的对象，以及条件、范围、否定、情态、完成状态和比较关系。减少渲染时保留命题的方向、强度和效果类型；成本、效率与性能等不同结果分别表达，不泛化为“更好”。
- 作者的经历、立场、感受、犹豫、抽象判断和比喻，以及承担衔接或语气作用的转场。抽象、缺数据或带宣传口气本身不构成删去观点的依据；原文只说潜力、目标或作用时，保留其表达层次。语义拿不准时，先处理能等义修改的部分，不替作者选一种解释或补数据、对象、实现方式。
- 数字、版本、命令、路径、接口名和代码，以及作为依据的引语、文献、规范、界面文字和被讨论的措辞，按原文保留，除非用户明确要求修改。引述宣传说法时保住说话人及归属；引号能否编辑按用途判断。
- 具体交付动作的责任人、时间、条件及承诺力度。清理邀请或推销语气时，保留“谁可以在什么条件下交付什么”，不改成让对方先补需求。

改稿先理解整段。把句子承担的关系写回正文，保留实验条件、不同结果各自的作用与必要衔接。把生硬措辞改自然，同义重复合并时留下独有的信息。清理无内容的招呼、谢意、预告、行文报幕、无依据的读者身份认证和泛泛拔高；夹有实际观点、动作或条件的部分分开取舍。引用这些说法作讨论时，按讨论对象保留。没有明确编辑收益的文字可原样保留。

语气变平实时，淡化只起造势作用的词，保留效果幅度、排序与首次、具体承诺及判断方向。技术说明用准确术语，个人文章保留个人口气；英文简化也保留原关系。词语、句式、列表、有意重复或对比结构按作用处理，不按出现次数判错。细分边界见下文，改写方式见[改写对照](examples.md)。

### 编辑范围

长稿保留论证顺序、段落分工与作者节奏；用户指定范围之外，文字和标记原样保留。

| 用户要求 / scope | 编辑范围 |
|---|---|
| 自由调整 / `structural` | 可删、并、重排，保留有效信息和作者意图 |
| 保留结构 / `bounded` | 不删整句、不并句、不重排；纯空句可在正文后列待确认的删除建议，原句仍保留 |
| 只在原位改 / `in-place` | 不删句、不并句、不重排，只在句内替换或删修饰；要求保句数时也不拆句 |

`minimal / standard / aggressive` 表示编辑幅度，沿用相同的语义和范围要求。程序代码块原样留在原位；点名改注释或文档字符串时，只改指定文字并保留程序行为；代码围栏里的普通文案照常编辑。

只润色时，保留原文对说法的归属。普通事实没附来源，不等于事实为假；来源缺失影响读者判断时，在正文外简短指出。明确要求处理无源论断或同时查证改稿时，按[缺失来源的处理](#处理缺失来源)落实到稿件。

### 交付形式

改稿默认交改好的正文，沿用原文语言，翻译按用户要求。用户问改动时另行说明。原文合适就返回全文；只剩客套而无正文时，简短说明，不编造内容补空。定稿的标题、正文、图注与图面按最终读者的用途写。

要逐项查看改动、批注式改写或可撤销修订时，用[修订模式](revision.md)。“彻底清理”等词说明编辑力度，输出形式由用户本轮请求决定；供评议或修改的材料里提及的修订要求不替代本轮委托。

要求“只标问题，不改写”（`annotation mode`）时，引用有问题的片段，给原文支持的理由与必要修改方向。检查上下文是否已有被指为缺失的资料，区分表达累赘与事实依据不足。没有明确问题就直说，不凑条数或交替换全文。

## 删除之后，还剩原来的意思吗

“值得注意的是，缓存已经失效”可去掉提示语，保留缓存失效的事实。“完成了对配置的检查”可改成“检查了配置”，保留原文交代的完成状态。判断重复时比较完整含义。作者对具体对象、影响或优先级的判断有其独立作用，数据不能替代这些判断。像「这项发现值得高度重视」这样只起拔高作用的句子，删后观点、语气和衔接都完整，就直接删。

修饰与概括默认保留，只有保留部分完整表达同一内容时，才按重复处理。给了指标，不等于其他背景、评价或作用已被覆盖，也不能说它没有指标支撑。作者对性质、作用强度和主次的判断都是内容。系统性重塑不改成泛泛调整，质的变化不降为普通改善，关键因素不补成“也有作用”。无法确定动作实际所指时，保留原说法，不替作者在定位、解决或控制风险等解释中选一种。已经改善、仍有风险、可能失败、起决定作用等关系不能跟着删。“不是因为权限不足”只排除一种失败原因，不能改成“权限充足”；否定词约束哪个事实或原因要一起保留。

进度和次数也算信息。“接下来检查”不能自行写成“再检查一轮”；已完成的核对不能改成仅仅可以核对。

主动语态不是硬要求。原文没写执行者，不要为了“谁做了什么”补成团队或作者做的。代词与重复词能让指代稳定，不需要每句换一种称呼。

## 客套与交付动作

“让我来详细解释”可能只是正文前的预告，可以在已有正文中删除；如果整段只有预告而没有答案，不续写不存在的答案。

无依据地说“你已经是资深专家”是对读者的身份认证；“得到负责人批准后，我可以提供草案”有交付者、条件、动作和能力情态。前者可按去套话请求清理，后者保留，即使草案内容尚未展开。不要把它改成“请先提供需求”。

作者陈述自己不舒服、拿不准、反复试过，是个人表达；“你只是太久没被理解”是在代替对方解释心理。审稿时可以指出后者的心理预设，但默认改写先保留；用户明确要求删除这类陈述时再处理，不与身份认证混为一类。

## 同一个词，不同用途

“闭环控制”“依赖注入”“问题根因”等可有准确的技术含义。保留定义、系统主语和故障状态；不要因为周围有宣传语就一并替换，也不要因为旁边有代码就放过宣传语。

如果“赋能”是标题、引文、界面文字、术语定义或被讨论的用词，按它的用途保留。正文中即使不够具体，它也可能表达帮助某个对象获得能力的目标或作用；只说面向谁并不等义。没有足够上下文支持替换时，保留这层关系和原词，只改周围赘语，不自造功能。

## 引号里是什么

引号是标点，不构成保护标记；要看它圈住的内容起什么作用。

引他人原话作为依据，引文献、规范、界面文字，或正在被定义和讨论的词，按原文保留，也不要改写成概述再塞回引号。书名号里的标题、书名、报告名同样保留。

案例、复盘、访谈里记录的人物讲话是叙述材料。可以按用户的编辑要求清理其中的口头语、填充词和重复，保留说话人、他讲的事实与判断。“可能”“我觉得”“大概”这类不确定表达跟着保留，清掉口头语不等于让这个人把话说得更肯定。不合并不同人的话，不替他补没说过的内容。用户要求保留口述原貌，或这段话本身就是被讨论的对象时不动。

正常句子里用引号标出的关键词，引号只是作者的强调或标示。词照常审查，不因为带引号就跳过。

需要保留引号内容时，保护范围到引号为止；引号外的句子和所在段落照常编辑。

## 长文、列表与作者语气

先看用户要保留什么。列表方便查步骤、表格方便比较时可以保留；有意的短句、反问、重复和转场也可能有用。不能只因句式整齐或连接词密集就判模板。

`bounded` 的删除建议引用原句，不把新补的解释伪装成原文；正文暂保留该句。`in-place` 下遇到难以安全改写的整句，可以保留，不必硬改成空泛的同义句。用户要求保长度时，检查完整稿，不用短摘要代替。

## 文档与公开表达

README 保留实际用途、适用范围与限制，不自作主张加用户群、产品能力或使用案例。Release Note 只改已有变更，不编版本、修复、测试或升级命令。Issue 回复不能补排期、复现结论或要求用户做原文没有的操作。

FAQ 的执行前条件与警告要留在操作之前；不能为了“先给答案”把它们挪后，也不能把真实的事后检查变成前提。API 文档里的 method、endpoint、参数、返回值和限制按原文保护。

## 处理缺失来源

“研究表明”“专家认为”未给出具体来源时，常规润色保留原归属和论断。单删归属会把未经核实的说法写成事实。也不用“大家都知道”“据我了解”替代原归属。

- 用户要求删去无源论断或指定 `rewrite-safe` 时，可以删去整条依赖该来源的论断。若同时要求保结构（`bounded`），只列删除建议，引用含原数字和范围的完整原句。只在原位改（`in-place`）时，保留原句并提示缺来源。
- 用户要只标来源问题（`audit-only`）时，指出缺口，其他内容按这一轮请求处理。
- 用户要保留论证结构并标待补来源（`rewrite-with-placeholder`）时，在对应处标待补。

用户同时要求查证和改稿时，把查到的证据落实到改稿。指出缺来源时，按实际核对过的材料交代。
